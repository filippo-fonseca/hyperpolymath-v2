# Phase 30 — Page of the Day / Daily Pages (PLAN)

Final phase of milestone v1.2 ("Wiki + In-Document JARVIS"). Adds a Daily
Pages surface to the Wiki: a calendar in the Wiki home that, on selecting a day,
idempotently opens (creating if needed) exactly one Daily Page for that day,
badged with a "Daily Page" pill, and carrying an automatic "process this page"
JARVIS button that runs the WHOLE page through the Phase 31 in-document engine to
generate a daily plan (tasks / events / captures). Supersedes the old Morning
Dump (no migration; this is its replacement).

## Requirements

- WIKI-DAILY-01 — Toggleable Daily Pages section in the Wiki home with a
  Journal-style calendar for navigating days.
- WIKI-DAILY-02 — Opening today (or any day) auto-creates exactly ONE Daily Page
  titled with the date; idempotent per user per day, race-safe, never duplicate.
- WIKI-DAILY-03 — A Daily Page shows a "Daily Page" pill badge under its title.
- WIKI-DAILY-04 — Daily Pages (and ONLY Daily Pages) show an automatic "process
  this page" JARVIS button that feeds the ENTIRE page through the shared engine to
  generate a daily plan, reusing the Phase 31 in-document @JARVIS pipeline.

## Task breakdown (one commit per unit)

1. **Migration + schema** — Add nullable `pages.daily_date` (`date`) column and a
   partial unique index `UNIQUE (user_id, daily_date) WHERE daily_date IS NOT
   NULL` to both `apps/web/lib/db/schema.ts` and a new SQL migration
   `apps/web/supabase/migrations/0035_pages_daily_date.sql`. Do NOT apply to prod.

2. **Query layer** — Thread `dailyDate: string | null` through `PageWithProjects`,
   `PAGE_COLS`, and `PageRow` in `apps/web/lib/db/queries/pages.ts`. Add
   `getDailyPagesForUser(userId)` → `{ id, dailyDate, title }[]` ordered by date.

3. **Server action** — Add idempotent, race-safe `openDailyPage(date)` to
   `apps/web/app/actions/pages.ts` (Zod-validated yyyy-MM-dd, getClaims auth,
   INSERT ... ON CONFLICT DO NOTHING + SELECT, returns `{ id }`, title via
   date-fns `EEEE, MMMM d, yyyy`). Add `getDailyPagesForCurrentUser()` wrapper.
   Extract the title formatter to a pure helper for unit testing.

4. **Calendar section (01)** — Generalize `JournalCalendar` to accept an optional
   `markedDates: Set<string>` (falling back to `entries` for `/journaling`), so it
   can drive both surfaces without breaking journaling. Add a collapsible "Daily
   Pages" section to `PagesListClient` with the calendar + a "Today" affordance;
   clicking a day calls `openDailyPage(iso)` then routes to `/wiki/{id}`.

5. **Pill + process button + editor exposure (03, 04)** — Add `onEditorReady?:
   (editor) => void` to `PageBlockEditor`; capture the live editor in
   `PageDetailClient`. When `page.dailyDate` is non-null, render a "Daily Page"
   pill under the title and a "process this page" button that calls
   `invokeInDocumentJarvis({ scopeOverride: "page", prompt: "Process this daily
   page: extract tasks, events, and captures and create them." })`. Add
   `scopeOverride?: ScopeKind` to `InvokeInDocumentArgs`; when set, build that
   scope's target directly (skip inference). Surface result via a sonner toast.

6. **Tests** — Vitest units: title formatter, idempotent dedup logic of
   `openDailyPage`, daily-pages query shape, and the `scopeOverride: "page"` path
   in `invokeInDocumentJarvis`. No brittle DOM calendar tests.

7. **Planning docs** — This PLAN + a SUMMARY at the end.
