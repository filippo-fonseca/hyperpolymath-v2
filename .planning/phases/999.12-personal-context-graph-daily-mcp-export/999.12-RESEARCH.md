# Phase 999.12: Personal context graph + daily MCP export — Research

**Researched:** 2026-06-09
**Domain:** Personal-knowledge graph + hosted MCP server + Drizzle/Supabase data layer + cron
**Confidence:** HIGH (MCP SDK + Vercel hosting + Drizzle/pgvector — all primary sources verified). MEDIUM on the exact shape of `Node`/`Edge` (no industry convention exists — proposal is principled but bespoke).

## Summary

This phase exports a typed daily snapshot of Filippo's first-party hyperpolymath signal (areas, projects, tasks, captures, training, habits, jarvis_facts) to a hosted MCP server so external Claude surfaces (claude.ai web, Claude Code) start every conversation already knowing him. Three concrete decisions emerge cleanly from the research:

1. **Use Vercel cron + a Next.js route handler guarded by `CRON_SECRET`** — not Supabase `pg_cron`. The snapshot builder runs typed TypeScript over Drizzle; staying on Vercel keeps it in one runtime/language.
2. **Host the MCP server on Vercel Functions (Node runtime, Fluid Compute) using `@modelcontextprotocol/sdk`'s `StreamableHTTPServerTransport` with bearer-token auth** — not stdio. Stdio would mean Filippo installs a binary per agent; hosted Streamable HTTP is the 2026 convention for remote MCP and is what Vercel/Notion/Linear all ship.
3. **Defer `query_context` (semantic search) to v1.1 of this phase.** Ship `get_current_context()` first. The snapshot is a graph payload — for ~50KB/day for a few months, the latest snapshot fully fits in Claude's context. Embeddings + pgvector add a second data-store concern that should not block the read-only MVP.

**Primary recommendation:** Land a thin, typed, versioned snapshot + a hosted MCP server with **two** v1 tools (`get_current_context`, `get_snapshot_history`); defer semantic query, mobile, write-back, and visualization. Mirror existing patterns — `integration_tokens` for bearer-token rotation, `apps/web/lib/training/` for the data layer, `apps/web/supabase/migrations/0024_*` for migration shape, `packages/jarvis-core/` for the standalone package.

### Locked Decisions

**Storage**
- New Postgres table `personal_context_snapshots` (per-day row, JSON payload)
- RLS policy: same `userId`-scoped pattern as every other table
- Schema versioning: `schema_version` integer column + versioned payload discriminator inside the JSON so the builder can evolve without rewriting history

- Pure server function in `apps/web/lib/context/` (mirrors training stats / insights data layers)

**Cron / scheduling**
- Default lean: Vercel cron hitting an internal API route guarded by a shared secret
- Nightly UTC midnight (user-local midnight is a future polish)
- Hand-rebuild button on the settings page for on-demand snapshot refresh

- Add `no_export` boolean column to `captures`, `tasks`, `jarvis_facts` (default false)

## Prior Art Survey

### Obsidian — graph from heterogeneous notes

Obsidian's graph view is the genre-defining example of "build a knowledge graph from unstructured personal notes." Three pieces of prior art are directly relevant:

- **Graph view internals** — Obsidian's graph is built from two primitives: notes (nodes) and `[[wikilinks]]` (edges). Every backlink becomes a graph edge automatically. This is the cleanest "graph from a heterogeneous corpus" pattern in the consumer software world. Lesson for us: keep `Node` and `Edge` as the only top-level shapes; everything else is a node property or edge type.
- **Dataview plugin** — `Dataview` lets users query the vault as if it were a typed database via DQL or JavaScript. Its key insight: **YAML frontmatter properties are the typed-data layer over freeform notes**. Lesson for us: the snapshot payload's `meta.properties` field per node is where typed structured fields live; the node itself stays generic.
- **Bases (Obsidian 1.9+)** — released 2026 as a Core Plugin, Bases turns YAML properties into queryable database views (Table, Cards, List, Map). Bases stores each query as a `.base` file in the vault; the data lives inline with the notes. Lesson for us: **the snapshot IS the source of truth for the export — it should be self-describing enough that an agent can answer "what fields are on a project?" without out-of-band schema**. Our `schema_version` + a self-describing payload (`payload.schema: { node_types: [...], edge_types: [...] }`) gives us this property.
- **Canvas** — Obsidian's spatial graph view (drag-arrange notes on an infinite canvas). Out of scope for v1 of this phase but worth noting as the visual model if/when we add a graph view in the web app (deferred per CONTEXT.md).

### Karpathy — LLM Knowledge Base + Context Engineering

Karpathy has been vocal in 2026 about two related concepts:

- **"Context engineering" over "prompt engineering"** (June 2025 X post, ~50K likes): "the delicate art and science of filling the context window." Direct quote: "People associate prompts with short task descriptions you'd give an LLM in your day-to-day use. When in every industrial-strength LLM app, context engineering is the delicate art and science of filling the context window."
- **LLM Wiki / Knowledge Base** (gist + multiple writeups, April 2026): plain-markdown personal knowledge base, maintained by Claude Code via an `agents.md` instruction file. The agent compiles raw notes into a structured wiki, then queries the wiki — **not the raw notes**. The compiler analogy: source notes → LLM compiler → structured wiki → queries.

**Lesson for us:** the snapshot is exactly Karpathy's "wiki" — a derived, structured, agent-friendly artifact built from the messy live data. Don't expose raw Supabase tables over MCP; expose the snapshot. This validates the architecture in CONTEXT.md.

### mem0 — memory layer for LLMs

- **Architecture:** two-stage (extract / update) using an LLM to extract facts from conversations, then ADD/UPDATE/DELETE/NOOP against a memory store. Graph variant uses entity nodes + relationship edges (Kuzu self-hosted, Neptune cloud). Raised $24M in Oct 2025.
- **Lesson for us:** mem0 is conversation-derived memory. Ours is **structured-data-derived** memory — a simpler problem, since we don't need an LLM extraction step. The snapshot builder is a pure deterministic function over Drizzle rows. This is a **dramatically simpler architecture** than mem0 and we should not import its complexity.
- **What to borrow:** the node-types + edge-types discriminated union shape generalizes well; mem0 uses similar.
- **What NOT to borrow:** mem0's full MCP server (over-scoped for our needs), its LLM-in-the-loop extraction (we don't need it), its graph DB layer (pgvector is enough for v1.1 semantic search).

### MCP server ecosystem (Linear, Notion, Filesystem)

- **`@modelcontextprotocol/sdk`** (TypeScript, npm `@modelcontextprotocol/sdk`) — current API surface: `McpServer` + transports (`StdioServerTransport`, `StreamableHTTPServerTransport`, deprecated `SSEServerTransport`). Tool schemas defined via Zod. Bearer-token auth via `requireBearerAuth` middleware for Express, or hand-rolled for the App Router.
- **Notion MCP** (official, `makenotion/notion-mcp-server`, v2.0.0 as of Sept 2025): hosted via Notion themselves. Tools use the prefix pattern (`notion-search`, `notion-fetch`). Tool schemas auto-generated from OpenAPI → Zod via a code-gen pipeline. **Architecturally relevant lesson:** Notion ships a hosted MCP; users add a URL + OAuth, not a binary install. This is the 2026 norm.
- **Linear MCP** — similar hosted pattern, snake_case tool names.
- **Naming convention** (analysis of first 100 MCP servers, zazencodes.com): >90% snake_case, ~95% multi-word (`fetch_forecast`), <1% camelCase. **Action:** use `get_current_context`, `get_snapshot_history` (NOT `getCurrentContext`). Tool names should be verb_noun.
- **Hosted MCP on Vercel** — Vercel ships a dedicated `vercel.com/docs/mcp` guide. They recommend Vercel Functions with **Fluid Compute** (not Edge) for MCP servers due to MCP's irregular usage pattern + Node-only dependency surface.

### Personal-knowledge competitors (shape, not features)

- **mem.ai** — "smart writing" with auto-linking. Their value is at the editing surface, not the data layer; not directly relevant.
- **Reflect** — backlinks + AI. Backlinks-as-edges is the Obsidian pattern.
- **Notion AI** — surfaces "what we already know" by retrieving relevant pages into context. They use a hybrid retrieval (keyword + embedding). This is exactly the v1.1 `query_context` pattern.
- **Lesson:** every serious personal-knowledge tool in 2026 ships hybrid search (keyword + vector). When we add `query_context`, do hybrid (tsvector + pgvector), not pure vector.

### Pattern 1: Pure deterministic snapshot builder

```typescript
// apps/web/lib/context/build-snapshot.ts
import { type Result, ok, err } from '@/lib/integrations/result';
import { db } from '@/lib/db';
import { z } from 'zod';

export const CURRENT_SCHEMA_VERSION = 1 as const;

const NodeSchema = z.discriminatedUnion('type', [
  z.object({ type: z.literal('area'), id: z.string().uuid(), name: z.string(), emoji: z.string().nullable(), orderIndex: z.number() }),
  z.object({ type: z.literal('project'), id: z.string().uuid(), areaId: z.string().uuid(), name: z.string(), isClass: z.boolean(), archived: z.boolean(), startDate: z.string().nullable(), endDate: z.string().nullable() }),
  z.object({ type: z.literal('task'), id: z.string().uuid(), title: z.string(), priority: z.enum(['P∞','P1','P2','P3']), status: z.enum(['not started','up next','in progress','almost done','lesno']), dueDate: z.string().nullable(), projectIds: z.array(z.string().uuid()) }),
  z.object({ type: z.literal('capture'), id: z.string().uuid(), text: z.string(), createdAt: z.string(), tags: z.array(z.string()), projectIds: z.array(z.string().uuid()) }),
  z.object({ type: z.literal('training_activity'), id: z.string().uuid(), kind: z.string(), durationMin: z.number().nullable(), distanceKm: z.number().nullable(), occurredAt: z.string() }),
  z.object({ type: z.literal('habit'), id: z.string().uuid(), name: z.string(), currentStreak: z.number() }),
  z.object({ type: z.literal('jarvis_fact'), id: z.string().uuid(), text: z.string(), createdAt: z.string() }),
]);

const EdgeSchema = z.discriminatedUnion('type', [
  z.object({ type: z.literal('project_in_area'), from: z.string().uuid(), to: z.string().uuid() }),
  z.object({ type: z.literal('task_in_project'), from: z.string().uuid(), to: z.string().uuid() }),
  z.object({ type: z.literal('capture_in_project'), from: z.string().uuid(), to: z.string().uuid() }),
  z.object({ type: z.literal('capture_tagged'), from: z.string().uuid(), tag: z.string() }),
  z.object({ type: z.literal('fact_about'), from: z.string().uuid(), entityType: z.enum(['area','project']), entityId: z.string().uuid() }),
]);

export const ContextSnapshotSchema = z.object({
  schemaVersion: z.literal(CURRENT_SCHEMA_VERSION),
  generatedAt: z.string(),
  nodes: z.array(NodeSchema),
  edges: z.array(EdgeSchema),
  meta: z.object({
    totalNodes: z.number(),
    totalEdges: z.number(),
    nodeCounts: z.record(z.string(), z.number()),
    excludedNoExportCount: z.number(),
  }),
});

export type ContextSnapshot = z.infer<typeof ContextSnapshotSchema>;

export async function buildSnapshot(userId: string): Promise<Result<ContextSnapshot>> {
  try {
    const [areas, projects, tasks, captures, training, habits, facts] = await Promise.all([
      loadAreas(userId), loadProjects(userId), loadTasks(userId),
      loadCaptures(userId), loadTraining(userId), loadHabits(userId), loadJarvisFacts(userId),
    ]);
    const nodes = [...areas.nodes, ...projects.nodes, ...tasks.nodes, ...captures.nodes, ...training.nodes, ...habits.nodes, ...facts.nodes];
    const edges = deriveEdges({ areas, projects, tasks, captures, facts });
    const snapshot: ContextSnapshot = {
      schemaVersion: CURRENT_SCHEMA_VERSION,
      generatedAt: new Date().toISOString(),
      nodes, edges,
      meta: {
        totalNodes: nodes.length,
        totalEdges: edges.length,
        nodeCounts: { area: areas.nodes.length, project: projects.nodes.length, /* ... */ },
        excludedNoExportCount: tasks.excluded + captures.excluded + facts.excluded,
      },
    };
    return ok(ContextSnapshotSchema.parse(snapshot));  // belt-and-suspenders
  } catch (e) {
    return err(e instanceof Error ? e.message : 'snapshot build failed');
  }
}
```

```typescript
// apps/web/app/api/cron/snapshot-context/route.ts
export const runtime = 'nodejs';
export const maxDuration = 60;

export async function GET(req: Request) {
  const auth = req.headers.get('authorization');
  if (auth !== `Bearer ${process.env.CRON_SECRET}`) {
    return new Response('Unauthorized', { status: 401 });
  }
  const users = await db.select({ id: usersTable.id }).from(usersTable);
  let written = 0;
  for (const { id } of users) {
    const r = await buildSnapshot(id);
    if (!r.ok) { console.error('snapshot failed', id, r.error); continue; }
    await db.insert(personalContextSnapshots)
      .values({ userId: id, snapshotDate: new Date().toISOString().slice(0,10), schemaVersion: 1, payload: r.data })
      .onConflictDoUpdate({ target: [personalContextSnapshots.userId, personalContextSnapshots.snapshotDate], set: { payload: r.data, schemaVersion: 1 } });
    written++;
  }
  return Response.json({ ok: true, snapshots_written: written });
}
```

### Pattern 3: MCP Streamable HTTP route (MCP-02, MCP-03)

```typescript
// apps/web/app/api/mcp/[...transport]/route.ts
import { McpServer } from '@modelcontextprotocol/sdk/server/mcp.js';
import { StreamableHTTPServerTransport } from '@modelcontextprotocol/sdk/server/streamableHttp.js';
import { createPersonalContextServer } from '@hyperpolymath/personal-context-mcp';
import { verifyBearer } from '@/lib/mcp/verify-bearer';

export const runtime = 'nodejs';
export const maxDuration = 60;

export async function POST(req: Request) {
  const auth = req.headers.get('authorization');
  const token = auth?.replace(/^Bearer\s+/i, '');
  if (!token) return new Response('Unauthorized', { status: 401 });
  const userId = await verifyBearer(token);
  if (!userId) return new Response('Unauthorized', { status: 401 });

  const server = createPersonalContextServer({ userId, db });
  const transport = new StreamableHTTPServerTransport({ /* config per SDK */ });
  await server.connect(transport);
  return transport.handleRequest(req);  // exact signature per current SDK docs
}
```

### Anti-Patterns to Avoid

- **Don't expose raw Supabase tables over MCP.** The snapshot is the contract. Raw-table exposure leaks schema churn and PII.
- **Don't share schema types between `apps/web` and `packages/personal-context-mcp` by import path.** The MCP package is deployable in isolation (future). Duplicate the Zod schemas in `packages/personal-context-mcp/src/types.ts` — or, better, lift the schemas into the package and have `apps/web` import them from there.
- **Don't write the MCP server as a stdio binary.** CONTEXT.md says stdio in the locked decisions, but research strongly recommends Streamable HTTP — flag this to the planner / user. Stdio means claude.ai web cannot consume the export at all.
- **Don't loop `buildSnapshot` over users in a single transaction.** Per-user is independent; failure on one shouldn't roll back the others. Use individual upserts.
- **Don't bypass `no_export` in `query_context` (v1.1).** Filter at builder time AND at query time defensively.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| MCP protocol framing | Custom JSON-RPC over HTTP | `@modelcontextprotocol/sdk` | Streamable HTTP spec has session IDs, init handshake, server-sent events — getting this wrong silently breaks clients |
| Bearer hashing | Custom HMAC scheme | `node:crypto` SHA-256 (matches `desktop_devices`) | Already in the codebase; reviewers know the pattern |
| Cron scheduling | Self-hosted node-cron / Inngest / Trigger.dev | Vercel cron | One config line in `vercel.json`; auto-authenticated via `CRON_SECRET` |
| Schema versioning DSL | Custom version-bump migrations | Plain `schemaVersion: 1` + a pure migrate function | Snapshots are immutable; migrations happen on read, not write |
| Result type | Custom error wrapper | `apps/web/lib/integrations/result.ts` | Already the convention; CONTEXT.md locks it |
| Token storage table | New `mcp_tokens` table | Reuse `integration_tokens` with `provider = 'mcp_agent'` | CONTEXT.md locks it; also matches "be lazy, reuse" |

**Key insight:** This phase is mostly **wiring existing patterns to a new domain**, not net-new infrastructure. The risky bits are (a) the MCP HTTP transport (new in 2025, still evolving) and (b) the schema-versioning discipline. Everything else is established hyperpolymath convention.

## Common Pitfalls

### Pitfall 1: Stdio vs HTTP transport mismatch
**What goes wrong:** CONTEXT.md says "stdio MCP server" but also says "hosted on Vercel." Stdio is a local-process transport — Vercel can't host stdio. Building stdio first and migrating later is a full rewrite of the route layer.
**Why it happens:** MCP's stdio transport is the older + better-documented option; the locked decision was written from training-data instinct.
**How to avoid:** Plan the MCP server with Streamable HTTP transport from day one. Flag this contradiction to the user during planning.
**Warning signs:** A `package.json` `bin:` entry; any `StdioServerTransport` import.

### Pitfall 2: Snapshot payload bloat
**What goes wrong:** Every capture and jarvis_fact's full text in the snapshot → snapshot grows to many MB → MCP responses exceed Claude's context window.
**Why it happens:** Defaulting to "include everything" makes the snapshot a copy of the DB.
**How to avoid:** Cap capture text to, say, 500 chars in the snapshot; cap to N most-recent items per type (e.g., last 50 captures, last 200 tasks not in `lesno`); always include all areas + active projects (those are the high-leverage context).
**Warning signs:** Snapshot row size growing super-linearly week-over-week; MCP tool responses > 100KB.

### Pitfall 3: Forever-snapshot schema lock-in
**What goes wrong:** A change to the Node shape breaks the reader for every historical snapshot. The history is "forever" so this is permanent damage.
**Why it happens:** Schema changes happen organically as new features land. Without a versioning discipline, old payloads become unparseable.
**How to avoid:** `schemaVersion: 1` from day one. Every Node/Edge addition bumps the version. The reader's job: if `payload.schemaVersion !== CURRENT`, route through `migrate(payload, fromVersion, toVersion)` — a pure function with explicit cases. **Never** mutate historical rows.
**Warning signs:** Reader code with `if (payload.foo ?? legacyDefault)` — that's an unmigrated schema drift.

### Pitfall 4: Plaintext token leak via Realtime
**What goes wrong:** If `integration_tokens` is in the `supabase_realtime` publication, the plaintext token (we only store hash, so this is moot here — but a regression risk) could leak via a Realtime broadcast.
**Why it happens:** Migrations often blanket-add tables to `supabase_realtime`. See 0024 for the pattern.
**How to avoid:** **Do NOT add `integration_tokens` or `personal_context_snapshots` to `supabase_realtime`** in 0026 / 0027. Snapshots don't need live updates anyway.
**Warning signs:** A `ALTER PUBLICATION supabase_realtime ADD TABLE personal_context_snapshots` line.

### Pitfall 5: `no_export` flag forgotten in v1.1 `query_context`
**What goes wrong:** Snapshot builder filters `no_export` rows. But if v1.1's embeddings pipeline embeds historical snapshots, and a snapshot was built before the user marked something `no_export`, that snapshot's embedding still surfaces the private content.
**Why it happens:** `no_export` is enforced at build time, not at query time. Historical snapshots are immutable.
**How to avoid:** In v1.1, when a row gets `no_export = true`, scrub it from all historical snapshots (UPDATE the JSONB payload to remove that node). Document the policy in `PRIVACY.md`.
**Warning signs:** A user complaint after toggling `no_export` and still seeing the content in a Claude session.

### Pitfall 6: Vercel cron only runs in production
**What goes wrong:** Local dev can't trigger the cron. First cron run is in production with zero observation.
**How to avoid:** Make `/api/cron/snapshot-context` callable from `/settings/context`'s "Rebuild now" button (CTX-08) — that's the manual trigger. Test extensively via the button before relying on the cron.

### MCP tool registration example

```typescript
// packages/personal-context-mcp/src/tools/get-current-context.ts
import { z } from 'zod';
import type { McpServer } from '@modelcontextprotocol/sdk/server/mcp.js';
import { loadSnapshot } from '../data/load-snapshot.js';

export function registerGetCurrentContext(server: McpServer, ctx: { userId: string; db: DB }) {
  server.tool(
    'get_current_context',
    'Returns the most recent personal context snapshot for the connected user. Optionally filter to specific topics (node types).',
    {
      topics: z.array(z.enum(['area','project','task','capture','training_activity','habit','jarvis_fact'])).optional()
        .describe('If provided, only nodes of these types are returned.'),
    },
    async ({ topics }) => {
      const snap = await loadSnapshot(ctx.db, ctx.userId);
      if (!snap) return { content: [{ type: 'text', text: 'No snapshot available yet.' }] };
      const filtered = topics
        ? { ...snap, nodes: snap.nodes.filter(n => topics.includes(n.type)) }
        : snap;
      return { content: [{ type: 'text', text: JSON.stringify(filtered, null, 2) }] };
    },
  );
}
```

## Open Questions

1. **Should the MCP server live in `apps/web/api/mcp/` or a separate Vercel project?**
   - What we know: CONTEXT.md says "separate package" (a workspace package, not necessarily a separate deployment). Mounting at `/api/mcp` in `apps/web` reuses the DB connection, env vars, and deployment pipeline.
   - What's unclear: Whether a future second user would justify isolating the MCP traffic to a different Vercel project for blast-radius reasons.
   - **Recommendation:** Mount in `apps/web` for v1. The `packages/personal-context-mcp/` factoring keeps the option open to extract later.

2. **Snapshot payload caps — what's "small enough"?**
   - What we know: Sonnet 4.6 has 200K default context (1M with beta header). A few-MB snapshot is fine; tens-of-MB is not.
   - What's unclear: Filippo's actual data volume in 6 months.
   - **Recommendation:** Plan caps from day one (50 most-recent captures, 200 active tasks, 500-char text truncation), document the caps in `PRIVACY.md`, and add a "snapshot size" metric to `/settings/context` so we can see growth.

3. **Does `get_snapshot_history` return full payloads or summaries?**
   - What we know: Full payloads for 30 days at ~500KB each = 15MB. Too large for a single tool response.
   - **Recommendation:** v1's `get_snapshot_history` returns metadata only (date, nodeCount per type, top-5 captures). The agent calls `get_current_context` for full payload. Document this in MCP-04 acceptance criteria.

4. **Should `query_context` (v1.1) be in this phase or its own?**
   - **Recommendation:** Its own phase (call it 999.12.1). Embeddings + pgvector + hybrid search is a 1-2 day chunk on its own; bundling it doubles the v1 scope and delays the read-only MVP that already delivers most of the value.
