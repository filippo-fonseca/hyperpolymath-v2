## Accomplishments

- `apps/web/lib/context/types.ts` ships the v1 Zod contract: NodeSchema discriminated union over `area | project | task | capture | training_activity | habit | jarvis_fact`, EdgeSchema discriminated union over `project_in_area | task_in_project | capture_in_project | capture_tagged | fact_about`, and the top-level `ContextSnapshotSchema` that enforces `schemaVersion: 1`, ISO generatedAt, and meta with totalNodes/totalEdges/nodeCounts/excludedNoExportCount.
- `apps/web/lib/context/migrate.ts` implements the forever-snapshot discipline (CTX-09): v1 payloads round-trip through Zod parse; future versions fail loudly with a clear error; older versions with no registered migrator return an opaque `_legacy: true` wrapper so the caller can drop rather than crash.
- `apps/web/lib/context/build-snapshot.ts` orchestrates seven loaders via `Promise.all`, derives edges purely over the loaded nodes, aggregates `nodeCounts` + `excludedNoExportCount`, and re-validates via `ContextSnapshotSchema.parse` before returning the `Result<ContextSnapshot>`. Never throws — exceptions wrap into `err(message)`.
- Seven per-node loaders in `apps/web/lib/context/nodes/` mirror `apps/web/lib/training/`'s data-layer pattern: each takes `(userId, db?)`, returns `{ nodes: Node[]; excluded: number }`, owner-scopes via denormalized `user_id` on junctions, applies caps from RESEARCH.md Pitfall 2, and (where applicable) reads `no_export` to gate + count.
- `apps/web/lib/context/edges.ts` exports the pure `deriveEdges()` function — zero DB access, walks loaded nodes, defensively drops project→area edges when the area isn't in the loaded set, only emits `fact_about` edges when both entityType and entityId are present (v1 doesn't expose those fields yet; future-proof).
- `apps/web/lib/context/persist.ts` exports `persistSnapshot()` doing the idempotent same-day upsert against `personalContextSnapshots` via `onConflictDoUpdate` on the composite `(user_id, snapshot_date)` PK, with `snapshotDate` defaulting to today UTC.
- 13 Vitest specs across two files: 5 in `migrate.test.ts` (version constant + all 4 migrate branches), 8 in `build-snapshot.test.ts` (empty user, Promise.all wiring, no_export count, no_export node-absence, full node assembly + edge derivation, error path, two purity tests for deriveEdges).

## Decisions Made

- **Loaders take `(userId, db?)` rather than mocked Drizzle chain.** Tests use `vi.mock('../nodes/{loader}', () => ({ loadX: vi.fn() }))` to swap loaders wholesale, then assert the buildSnapshot contract directly (Promise.all wiring, aggregate meta, Result envelope). Faster, cleaner, and decoupled from query-builder DSL. The loaders' own SQL correctness is implicit from CTX-04 grep-verifiable wiring and a future integration test against pglite/staging Postgres.
- **Edges are derived purely from loaded nodes — no second DB round trip.** The captures and tasks loaders fetch their junction rows inline once (scoped via the denormalized `user_id` on junction tables, no JOIN through the parent table needed). deriveEdges then walks the in-memory nodes only. Keeps complexity O(rows), keeps deriveEdges trivially unit-testable.
- **Caps live in loaders, not the schema (RESEARCH.md Pitfall 2).** ContextSnapshotSchema accepts arrays of any cardinality. Tasks loader: 200 cap with 250-row query window so excluded count approximates the recent activity window. Captures: 50 cap, 500-char text truncation. Training: 30 cap. Habits/jarvis_facts/areas/projects: no cap (small sets per user).
- **noExport gate enforced in TS, not WHERE.** Loaders SELECT `no_export` and skip-with-count rather than `WHERE no_export = false`. Two reasons: (a) meta.excludedNoExportCount surfaces the count to the user without a second COUNT(*) query, and (b) defensive — if a row flips noExport mid-build, we still count it correctly.
- **Zod 4 UUID strict-format gotcha logged inline in the test.** `z.string().uuid()` accepts only v1–v8 UUIDs (or the all-zero / all-ff sentinels). Pad-counter fixtures like `00000000-…-0010` fail format. All test fixtures use `crypto.randomUUID()` (v4). Comment block in the test file documents the rationale.
- **Habit `currentStreak` = walk-backwards-from-today over habit_completions WHERE status='done'.** Simplest correct interpretation: "how many consecutive days has Filippo kept this up." Per-day-of-week schedule math (days_of_week) is the habit-management surface's concern, not the snapshot's.
- **Training `distanceKm` / `durationMin` prefer actual over planned.** Snapshot answers "what happened" — actual when present, planned as fallback for activities still on the board. Canonical km storage passes through unchanged.
- **`payload` cast at the persist call site** (`snapshot as unknown as Record<string, unknown>`) because Plan 01 deliberately typed `personalContextSnapshots.payload` as plain `jsonb` (no `.$type<ContextSnapshot>()`) to avoid a `schema.ts → build-snapshot.ts → schema.ts` circular import.
- **`--no-verify` on per-task commits.** Per orchestrator-explicit guidance — orchestrator validates after.

## Deviations from Plan

None of the rule-grade variety. The plan executed exactly as written across all three tasks. One minor variance was forced by Zod 4 behavior:

- **Test fixtures switched from pad-counter UUIDs to `crypto.randomUUID()` (Rule 1 — Bug, but mine, in the test fixture).** The plan suggested `00000000-…-${n.toString().padStart(12, '0')}` for deterministic-looking IDs in test data. Zod 4's `z.string().uuid()` rejects those (strict v1–v8 + sentinel format). Switched to `crypto.randomUUID()` and stored values in variables for cross-call referential equality. Documented inline in the test file. No production code changed.
