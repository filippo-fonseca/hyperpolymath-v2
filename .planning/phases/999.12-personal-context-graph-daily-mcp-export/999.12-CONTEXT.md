# Phase 999.12: Personal context graph + daily MCP export — Context

**Gathered:** 2026-06-09
**Status:** Ready for planning

<domain>
## Phase Boundary

Build a single always-current personal-context graph that unifies every
first-party signal in hyperpolymath (areas, projects, tasks, captures,
training, habits, JARVIS facts, settings) plus a small set of opt-in
external inputs (Linear / GitHub activity, calendar load, recent reading)
into a typed graph snapshot. Persist one snapshot per day. Expose the
latest snapshot — and a semantic-query interface over snapshot history —
to external agents via a hosted MCP server using long-lived per-agent
bearer tokens.

**In scope**
- Server-side snapshot builder (pure function reading from each surface)
- `personal_context_snapshots` Postgres table with versioned JSON payload
  + RLS scoped to `userId` like every other table in the system
- Daily cron job (Vercel cron OR Supabase pg_cron — decided in research)
  that materializes a snapshot and persists it
- Privacy gate: per-row `no_export` flag on captures + tasks + facts so
  personal items never leave Postgres
- MCP server (separate package, hosted) exposing at minimum:
  - `get_current_context()` → latest snapshot, possibly trimmed by topic
  - `query_context(question)` → semantic search over snapshot history
- Per-agent bearer tokens stored in a token-rotation table (`integration_tokens`
  pattern already exists for Strava — reuse, don't reinvent)
- Settings surface in the web app to view / mint / revoke MCP tokens
- Schema versioning for the snapshot payload (snapshots are forever; the
  payload schema will evolve)

**Out of scope (this phase)**
- Write-back MCP tools (e.g., `add_capture` from an external agent) — read-only first
- Mobile app surface — that's 999.11
- Real-time streaming of context (snapshots are nightly + on-demand only)
- Multi-user MCP tenancy beyond the existing `userId`-scoped RLS
- Replacing the LifeOS homepage with a graph view (visualization is a future enhancement)

</domain>

<decisions>
## Implementation Decisions

### Storage
- New Postgres table `personal_context_snapshots` (per-day row, JSON payload)
- RLS policy: same `userId`-scoped pattern as every other table
- Schema versioning: a `schema_version` integer column + a versioned payload
  discriminator inside the JSON so the builder can evolve without rewriting
  history

### Snapshot builder
- Pure server function in `apps/web/lib/context/` (mirrors how training stats /
  insights data layers are factored)
- Reads via Drizzle from each existing surface (areas, projects, tasks,
  captures, training, habits, jarvis_facts) — NEVER duplicates writes back
  into Postgres
- Emits a typed graph: `{ nodes: Node[]; edges: Edge[]; meta: { ... } }`
  where Node/Edge are discriminated unions in TypeScript with Zod validation

### Cron / scheduling
- **Decision: Vercel cron** (over Supabase pg_cron). The builder is
  TypeScript over Drizzle; pg_cron would force a PL/pgSQL port (unacceptable)
  or a pg_cron→net.http_post→Vercel route hop (no benefit). Vercel cron + a
  `CRON_SECRET` bearer is one line in `vercel.json`
- Nightly UTC midnight (user's local midnight is a future polish)
- Hand-rebuild button on the settings page for on-demand snapshot refresh

### Privacy
- Add a `no_export` boolean column to `captures`, `tasks`, `jarvis_facts`
  (default false). Snapshot builder filters those rows out
- A `no_export` toggle in the relevant UI surfaces (capture detail, task
  detail, JARVIS fact list)
- Document the exact set of fields exported vs. dropped in a `PRIVACY.md`
  inside the MCP package

### MCP server
- Separate package: `packages/personal-context-mcp/` (matches the
  `packages/jarvis-core/` factoring already in the repo) — exports the
  typed tool definitions + handlers
- **Transport: Streamable HTTP** via `@modelcontextprotocol/sdk`'s
  `StreamableHTTPServerTransport`. stdio is local-process only and cannot
  serve claude.ai web — corrected after research surveyed the 2026 MCP
  ecosystem (Notion / Linear / Vercel docs all converge on Streamable HTTP
  for hosted MCPs)
- Hosted as a Next.js API route at `apps/web/app/api/mcp/route.ts` (NOT a
  separate Vercel project — keeps the DB connection + env vars in one
  place; the `packages/personal-context-mcp/` factoring keeps the option
  open to extract later)
- Authenticates via long-lived bearer token in the `Authorization` header,
  validated against `integration_tokens` (`provider = 'mcp_agent'`)
- Tools (v1 — read-only):
  - `get_current_context(args?: { topics?: string[] })` → latest snapshot,
    optionally trimmed to a topic subset (e.g., just `training` + `tasks`)
  - `get_snapshot_history(args?: { days?: number })` → metadata-only list
    of recent snapshots (no payloads — payloads can be 100s of KB)
- Tools deferred to follow-on phase **999.12.1**:
  - `query_context({ question: string, k?: number })` → semantic search
    over snapshot history (embeddings + pgvector + hybrid search is its
    own 1–2 day chunk; bundling it doubles v1 scope)

### Semantic query (DEFERRED to phase 999.12.1)
- Embeddings + pgvector + `query_context` MCP tool deferred to a follow-on
  phase. Read-only snapshot retrieval (`get_current_context` +
  `get_snapshot_history`) delivers most of the value in v1; semantic search
  is additive and can ship a few weeks later without breaking anyone

### Tokens
- Reuse the existing `integration_tokens` table pattern shipped for Strava
- New per-agent token type: `mcp_agent`
- Settings page surface to mint, list, and revoke tokens (mirror /settings/desktop)

### Claude's Discretion
- The exact JSON shape of `Node` and `Edge` (research will propose; planner finalizes)
- Whether to ship semantic query in v1 or defer to v1.1 of this phase
  (lean: defer if it adds material complexity; ship `get_current_context()` first)
- Token rotation cadence (90 days default is fine)
- Whether to mirror the snapshot into a separate `context_snapshots_embeddings`
  table or keep embeddings inline in the same row

  similar) so the user can SEE what's being exported — debug + transparency

  tasks, captures, training, habits, JARVIS facts. Externals (Linear / GH
  / calendar load / recent reading) are explicitly **opt-in** per node type

  share the Supabase DB connection but should not import from `apps/web/`
  (use `packages/personal-context-mcp/` as the only shared module)
