# Phase 05.1: jarvis-agentic-refactor - Context

**Gathered:** 2026-05-17
**Status:** Ready for planning

<domain>
## Phase Boundary

Reshape JARVIS — already shipping create-only in Phase 5 — into a high-efficiency agentic assistant that feels like Tony Stark's JARVIS: conversational, witty, persistent across sessions, and pipeline-clean. Four concrete deliverables: (1) a prose-first response surface with dry-wit personality on top of compact receipts; (2) a persistent `jarvis_facts` memory layer that survives across sessions (behavioural preferences, workflow rules, entity aliases, recurring patterns); (3) an `ask_clarification` tool for medium-confidence cases where capture-first is the wrong fallback; (4) a per-turn pipeline-efficiency audit with a concrete latency + DB-roundtrip budget. Builds incrementally on the Phase 5 jarvis-core / Node-runtime SSE route / Console UI — does NOT rewrite from scratch. Implicit-intent extraction from fragmented language ("dinner 8pm with anna. need to buy flowers friday.") matches the fidelity of explicit phrasing ("Jarvis, schedule X and remind me Y") — verified by an expanded adversarial + implicit-intent fixture suite.

**Out of scope (push to other phases or backlog):**
- Voice / TTS / wake-word → Phase 7
- General read-back tools (`list_tasks`, `search_captures`, `list_events`) → backlog 999.3 — *exception:* `/ask` mode is allowed to read `jarvis_facts` only, since memory is the topic of this phase
- Update / Delete via JARVIS → JARVIS-V2-01..03 (post-MVP per PROJECT.md)
- New domains beyond Areas / Projects / Tasks / Captures / gcal
- Multi-tenancy or shared memory across users
- Server-side embedding / RAG retrieval (pgvector) — single-user, fact count stays small enough for whole-blob prompt injection

</domain>

<decisions>
## Implementation Decisions

### Response Surface & Personality

- **D-R1: Conversational prose IS the primary response surface; receipts are supplementary.** Each turn renders, in order: (a) one prose line (1-3 sentences) authored by the model — opens with a JARVIS-register acknowledgment ("Handled, sir.", "Very good.", "Noted."), states what was done in natural language, optionally appends a single dry observational aside; (b) compact receipt cards below — resolved fields + Undo + 5s countdown — visually de-emphasized vs current Phase 5 receipts (smaller, lighter borders, footer-style). User's canonical example (treat as the gold reference): *"Handled, sir. Dinner with Anna is set for Saturday at 8 PM, and I'll remind you Friday to pick up flowers. I'd recommend not showing up empty-handed unless your plan is to rely entirely on charm again."*
- **D-R2: Personality calibration — wit when natural, brevity when not.** Carries Phase 5's D-16 British/dry/formal/never-sycophantic register intact. **Adds:** 1-3 sentences per turn (up from "one sentence per action receipt"). Dry observational wit is permitted and welcome when the situation invites it (recurring entity, multi-action coordination, the user's choice has texture worth commenting on) — but NEVER mandatory. Default is concise acknowledgment. The wit ceiling is the canonical example above; the floor is *"Noted, sir. Friday."* The user is Filippo — Yale undergrad, builds in public — JARVIS knows this, but doesn't fawn over it.
- **D-R3: How the model emits prose alongside actions.** Anthropic Sonnet 4.6 emits interleaved `text` + `tool_use` content blocks natively. The model is instructed (system prompt) to emit ONE leading `text` block per turn that summarises the actions it's about to take, in JARVIS register, then the `tool_use` blocks. The Console renders the leading `text` as the prose line; the `tool_use` blocks become the compact receipts below. Phase 5's "tool calls only, no narrative prefix" rule (personality.ts:48) is **reversed** for this phase. Adversarial defence still requires that meta-question / ask-mode replies remain prose-only with no tool_use.
- **D-R4: Slash command set preserved.** `/task`, `/capture`, `/event`, `/ask`, `/help` stay. `/ask` mode now MAY read `jarvis_facts` (and that table only) — useful for "what do you remember about me?". Read-back of tasks / captures / events remains backlog 999.3.

### Persistent Memory Layer

- **D-M1: New `jarvis_facts` Postgres table is the source of truth for persistent memory.** Schema (additive migration): `id uuid pk, user_id uuid fk, type text check in ('preference','rule','entity','workflow'), key text, value text, source text check in ('user_explicit','jarvis_suggested'), created_at timestamptz, updated_at timestamptz, last_used_at timestamptz nullable`. RLS scoped on `(SELECT auth.uid()) = user_id`. Indexed on `(user_id, type)` + `(user_id, last_used_at DESC)`. Editable in a new Settings → Memory surface (read/edit/delete; create rare — almost everything written by JARVIS).
- **D-M2: Fact taxonomy.** Four types, semantics locked here:
  - `preference` — behavioural prefs ("be concise", "always use 24-hour time", "no exclamation marks")
  - `rule` — workflow rules ("remind me 1 day before every event", "default events to my Yale calendar")
  - `entity` — aliases / recurring proper nouns ("Anna = my partner", "the lab = $rocketry project")
  - `workflow` — recurring patterns observed ("typically schedules gym Mon/Wed/Fri at 6am") — model-suggested only
- **D-M3: When facts are written.** Two paths, both auditable:
  - **User-explicit:** user says "remember that...", "from now on always...", "Anna is my partner" → model emits a new `remember_fact` tool call → server inserts row with `source='user_explicit'`. Receipt shows the fact + 5s undo (hard delete).
  - **Model-suggested:** model detects a recurring pattern or referential ambiguity (e.g. user said "Anna" 3rd time without an alias) → model emits `remember_fact` with `source='jarvis_suggested'` AND prose asking "Shall I remember that?" The receipt has a "Keep / Discard" affordance (default: keep, 10s window before auto-persist). Suggested facts NEVER persist silently — always a visible receipt.
  - Hard rule: facts never written purely from model inference without a user-visible receipt.
- **D-M4: How facts surface to the model.** All current `jarvis_facts` for the user are compiled into a compact text block inside the cached system-prompt segment on every turn. Single-user scale means total fact count stays small (<200 expected lifetime); the compiled block fits inside the existing prompt-cache window. No retrieval, no embedding — whole-blob injection. When `jarvis_facts` is updated, the cache key rotates on next turn (one cold-cache turn is acceptable cost).
- **D-M5: `remember_fact` is the fifth JARVIS tool.** Schema: `remember_fact(type, key, value, source)`. Strict Zod, same pipeline as the existing 3 tools. Adversarial defence: never written from a Capture's content (only from the user's CURRENT-turn message). The injection-defence test suite gains 2-3 new fixtures.
- **D-M6: Memory edit surface.** New `/settings/memory` page lists all facts grouped by type with inline edit + delete + "last used" timestamp. No new components: reuses Phase 2's table primitives. Out of scope for THIS phase: usage analytics, fact merge UI, conflict resolution beyond last-write-wins.

### Ambiguity & Clarifying Questions

- **D-A1: New `ask_clarification` tool — the 5th create-tool, but emits a question, not an action.** Schema: `ask_clarification(question, options?: string[], suggested_action?: { tool, args })`. Model emits this when confidence is medium-low AND capture-first would be the wrong fallback (e.g. ambiguous date, unresolvable `$project` reference where a similar one exists, multiple plausible event durations). Strict Zod. Adversarial defence: question content is NEVER a stored fact / persistent state — it lives in the scrollback only.
- **D-A2: UX of clarification.** The clarification renders inline as a special action receipt with: the question, optional preset answer chips (from `options[]`), a free-text reply input that submits as the NEXT user turn. The user's reply continues the same logical turn — the model receives `[CLARIFICATION REPLY] ...` as part of the next message. If the user ignores the clarification and types something new, the original turn closes and the new input starts a fresh turn (the unanswered clarification stays in scrollback as a record).
- **D-A3: Confidence threshold heuristic.** The model self-decides (no server-side confidence gating). System-prompt rule: emit `ask_clarification` ONLY when (a) capture-first would lose information the user clearly intended to file as a specific type, OR (b) a `$project` / `#hashtag` / date has multiple plausible resolutions. For genuinely ambiguous noise ("man, I miss Anna") — capture-first wins, no question asked.
- **D-A4: Backstop — capture-first remains the default.** Phase 5's JARVIS-06 / JARVIS-17 still apply unchanged. Clarifying questions are the *exception*, not the new default. Adversarial fixtures still demand that injection-style prompts route to Capture without clarification.

### Pipeline Efficiency & Budget

- **D-P1: Concrete per-turn budget, asserted by a new perf test.** Targets:
  - **TTFA (time to first action emit), warm cache:** p50 < 800ms, p95 < 2.5s
  - **TTFA, cold cache:** p50 < 3s, p95 < 8s (matches existing JARVIS-15 V1, holds the line)
  - **DB roundtrips per single-action turn:** ≤ 2 (one for project/calendar reference validation, one for executor write) — measured by Drizzle query log in the perf test
  - **No incidental refetches on shell components (Sidebar areas/projects)** triggered by JARVIS Server Actions. Asserted via test that mounts Sidebar + invokes a JARVIS undo Server Action and counts areas-query refetches (must be 0).
- **D-P2: Root-cause fixes for the observed waste.** Three known sources to address:
  1. **Sidebar areas/projects refetch on every JARVIS Server Action.** Root cause to verify in research/planning phase: likely Next.js revalidate-after-Server-Action triggering a TanStack Query refetch (refetchOnMount or staleTime miss) + Realtime captures invalidation fanning out unnecessarily. Fix candidates: bump staleTime on areas/projects queries, ensure JARVIS Server Actions don't call `revalidatePath` for `/today`, audit `useTableSubscription` for unintended cross-table invalidation.
  2. **`getAreasForCurrentUser` called from JARVIS surfaces that don't need it.** `/today` only needs projects + hashtags + timezone (page.tsx:23-42 already correct — but Sidebar fires it). Move areas to a query that's truly idle on /today.
  3. **`validate-references` query batching.** Currently one query per reference type; combine into a single round-trip when multiple references are present in one turn.
- **D-P3: Action-graph internal data structure.** Adopt your spec's `intent → entity → multi-action decomposition → context enrichment → action graph generation → parallel execution → result aggregation → response synthesis` mental model — but implement it WITHOUT a full route rewrite. The pipeline stays SSE-streaming; "action graph" is the in-memory shape of the parallel `tool_use` blocks the model already emits via Anthropic's native parallel_tool_use (Phase 5 already does this). The delta is: (a) executor runs tool_use blocks via `Promise.all` instead of sequential `for...of`; (b) per-block executor results stream back as they complete (not in original order) — Console renders receipts in completion order with a "queued" placeholder for in-flight blocks; (c) on partial failure, completed actions stay, failed ones surface with retry affordance.
- **D-P4: Implicit-intent test corpus.** New test file `tests/jarvis-implicit-intent.test.ts` with ~20 fixtures pairing fragmented and explicit phrasings of the same intent; the LIVE model (or a recorded-fixture replay if cost matters) must produce structurally-equivalent action sets for both. Source pairs from the user's spec examples:
  - "dinner 8pm with anna. need to buy flowers friday." ≡ "Jarvis, schedule a dinner with Anna at 8pm on Saturday and remind me to buy flowers on Friday."
  - "tmrw 6am gym + standup 10" ≡ "remind me to go to the gym tomorrow at 6am and put my standup on the calendar at 10am"
  - …plus ~18 more pairs spanning multi-action / entity-recall / priority-inference / date-fragment cases. Goal: ~95%+ structural equivalence (same tool, same key fields).

### Claude's Discretion (Planner / Researcher decides)

- Exact wording / additions to the personality system prompt (use D-R1 canonical example as the calibration target)
- Where the leading `text` block sits in the SSE stream relative to first `tool_use` (probably before, but the Console can handle either)
- `remember_fact` UI styling (looks like a thinner action receipt; exact treatment a planner call)
- Fact taxonomy edge cases (a "rule" that's also an "entity"? Pick one, prefer rule)
- Exact perf-test mechanism (Drizzle query-log spy vs Supabase explain plan vs raw timing)
- Whether parallel-tool-use needs an upper bound (e.g. cap at 5 simultaneous tool_use blocks per turn to keep latency stable)
- Whether ask_clarification's reply-as-next-turn flow needs server-side correlation IDs or can rely on conversation order
- Migration ordering for `jarvis_facts` table relative to any other in-flight schema work

## Specific Ideas

- The user's canonical prose example is the gold standard for personality calibration — every change to `personality.ts` should be tested against this output for a 2-action prompt about Anna
- Filippo is the user; JARVIS knows he's a Yale undergrad, builds in public, and ships fast — references to identity stay sparing, never fawning
- The witty observational asides should feel like Tony Stark's JARVIS commenting on something genuine in the moment — not generic AI-assistant humor. "I'd recommend not showing up empty-handed unless your plan is to rely entirely on charm again" works because it's specific to the dinner-with-Anna context. Generic ("Good luck!") doesn't
- Pipeline cleanup is graded on observable user impact: if /capture for "Man, I miss Anna" still triggers extra DB queries after this phase, the phase failed regardless of test counts
- Memory should feel like JARVIS quietly building a model of Filippo over time — not a CRUD form the user has to manage. Settings → Memory exists as escape valve, not the main interaction

## Deferred Ideas

- **Action-graph DAG with dependency edges** (parts of user's "dependency resolution" goal) — Phase 5's parallel_tool_use covers independent multi-action; explicit serial dependencies ("create event, then create a task that's due 1 day before the event") need a graph executor with edges. Captured for a future phase or backlog item — out of scope for 05.1 to keep the perf budget reachable.
- **Speculative execution / pre-emptive UI** — render receipt placeholder before the model emits, swap on real emission. Speed win but adds optimistic-state complexity; defer.
- **Cross-fact reasoning** — "Anna is my partner" + "always remind 1d before partner events" → automatic reminders on Anna-events. Requires fact composition logic; punt to a memory-V2 phase.
- **Fact merge / conflict resolution UI** — for now, last-write-wins. Merge UX deferred.
- **Memory analytics (most-used facts, stale-fact warnings)** — deferred to Phase 6 polish or a future memory phase.
- **Voice-aware prose ceiling** — when voice ships in Phase 7, the prose response may need a shorter spoken variant. That ties to the existing `voice_summary` field, so this is already partially handled — but a coherent voice/text register split is Phase 7's problem.
- **Read-back of tasks/captures/events from /ask** — stays backlog 999.3; this phase only opens `/ask` to read `jarvis_facts`.
