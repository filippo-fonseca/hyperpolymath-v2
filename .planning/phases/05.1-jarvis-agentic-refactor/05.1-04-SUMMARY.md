# Phase 5.1 Plan 04: Clarification + Implicit-Intent Corpus Summary

ask_clarification registered as the 5th JARVIS tool with inline question receipt (chip options + free-text reply), depth cap via [CLARIFICATION REPLY] prefix detection, and 20-fixture mocked dispatcher regression corpus that guards structural equivalence without live API calls.

## What Was Built

### Task 1: ask_clarification Tool + Personality + Route Wiring (commits: 51844ef)

**Tool definition** (`packages/jarvis-core/src/tools/ask-clarification.ts`):
- `zAskClarificationFor({ voiceActive })` factory — `question` (1-300 chars), optional `options` (≤5 chips, ≤80 chars each), optional `suggested_action` with tool enum + args
- Zod 4.4.3 API: `z.array(...).max(5, "msg")` requires error message as 2nd arg; `z.record(z.string(), z.unknown())` requires explicit key type

**Tool registration** (`packages/jarvis-core/src/tools/index.ts`):
- 5th tool added to `buildToolDefinitions()`; cache_control moved from `remember_fact` to `ask_clarification` (new LAST tool)
- Tool count: 4 → 5; cache breakpoint re-anchored

**Personality rules** (`packages/jarvis-core/src/personality.ts`):
- "four tools" → "five tools: create_task, create_capture, create_event, remember_fact, ask_clarification"
- ASK_CLARIFICATION RULE added: "it must be alone in the turn", depth cap note, capture-first remains default
- Dinner-with-sam ask_clarification example added to EXAMPLES

**Route wiring** (`apps/web/app/api/jarvis/route.ts`):
- `ask_clarification: zAskClarification` added to TOOL_VALIDATORS
- Depth cap: `isClarificationReply = body.input.trimStart().startsWith("[CLARIFICATION REPLY]")` → appends `[INTERNAL: ...]` system note to userContent
- Dispatcher: emits `sse("clarification", {toolUseId, question, options, suggestedAction})` BEFORE calling executor.askClarification

**Executor no-op** (`apps/web/lib/jarvis/executor.ts`):
- `askClarification(input, ctx)` returns `{ok: true, id: "clarification:<uuid>", receipt: {question, options, suggested_action}}` — no DB write
- `ActionExecutor` interface extended with `askClarification` method

**Stream client** (`apps/web/components/jarvis/jarvis-stream-client.ts`):
- `JarvisClarificationEvent` interface added
- `onClarification?: (data: JarvisClarificationEvent) => void` callback added to `JarvisCallbacks`
- `clarification` event branch added to SSE reader

### Task 2: JarvisClarification UI + Console Correlation (commit: f4983b8)

**Types** (`apps/web/components/jarvis/jarvis-types.ts`):
- `ScrollbackClarification` interface: `toolUseId, question, options[], suggestedAction, answered: boolean`
- `clarification?: ScrollbackClarification` field on `ScrollbackAssistantTurn`
- `ScrollbackAction.name` union includes `"ask_clarification"`

**Component** (`apps/web/components/jarvis/JarvisClarification.tsx`):
- Question text with HelpCircle badge + violet border
- Chip Button options (hidden when answered or no onReply)
- Input + Send button for free-text reply
- `answered` indicator text when disabled
- `onReply(text)` fires WITHOUT the `[CLARIFICATION REPLY]` prefix — Console adds it

**Console** (`apps/web/components/jarvis/JarvisConsole.tsx`):
- `onClarification` callback stores clarification on current assistant turn via `setTurns`
- `handleClarificationReply(turnId, text)`: marks answered, calls `handleSubmit({input: '[CLARIFICATION REPLY] ${text}'})`
- Any new user turn marks all prior unanswered clarifications as `answered: true` (last-question-wins)

**Scrollback** (`apps/web/components/jarvis/JarvisScrollback.tsx`):
- `onClarificationReply?: (turnId, text) => void` added to Props
- JarvisClarification rendered AFTER prose BEFORE action receipts when `turn.clarification` exists

**Receipt** (`apps/web/components/jarvis/JarvisReceipt.tsx`):
- `ask_clarification` entry in INTENT_META: `{label: "QUESTION", icon: HelpCircle, classes: "border-violet-500/50 bg-violet-500/5"}`

**Tests** (`apps/web/tests/jarvis-clarification.test.tsx`):
- 9 tests: renders question+chips+input, chip click calls onReply, second chip, Enter key, Send button, answered state, no onReply → disabled, QUESTION header, no-options mode

### Task 3: Implicit-Intent Corpus + Dispatcher Regression (commit: 2d48956)

**Fixtures** (`apps/web/tests/jarvis-implicit-intent.fixtures.ts`):
- 20 `ImplicitIntentFixture` entries pairing `fragmented` vs `explicit` phrasings
- Each fixture has `expectedTools[]` with `name` and `keyFields` (RegExp for semantic, string for exact)
- Covers: events, tasks, captures, priorities (P1/P2/P∞), multi-action turns, 3x duplicate-tool sets

**Test runner** (`apps/web/tests/jarvis-implicit-intent.test.ts`):
- Full vi.hoisted mock setup mirroring jarvis-route.test.ts (Supabase, Anthropic SDK, DB, telemetry, executor, facts)
- `buildAnthropicStream`, `readSseEvents`, `buildRequest` verbatim from route test harness
- `runScriptedTurn(input, scripted)` — mocks Anthropic SDK, POSTs to real route handler, reads SSE events, returns action payloads
- `synthesizeInputFromKeyFields(keyFields, toolName)` — extracts first literal alternative from RegExp; injects `start`/`end` placeholders for `create_event` (required by Zod schema)
- `toolsStructurallyEqual(a, b, expected)` + `satisfies(actions, expected)` with match-and-consume `findIndex` (handles 3x gym duplicate events)
- `keyFieldsMatch(input, keyFields)` with ±1-day date tolerance
