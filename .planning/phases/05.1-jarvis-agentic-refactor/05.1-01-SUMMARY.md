# Phase 05.1 Plan 01: Pipeline Efficiency Summary

One-liner: Sidebar areas query made permanently fresh via `initialDataUpdatedAt: Date.now()` + `staleTime: Infinity`; validate-references batched into a single `Promise.all` roundtrip via `validateTurnReferences`; perf budget asserted by Drizzle-mock query counter.

## What Changed

### Task 1: Sidebar areas/projects refetch fix + regression test

**2-line patch to `apps/web/components/shell/Sidebar.tsx` (lines 92-101):**

Added `initialDataUpdatedAt: Date.now()` and `staleTime: Infinity` to the areas `useQuery`. Without these:
- TanStack Query 5 treated `initialData` without a timestamp as `updatedAt: 0` (instantly stale)
- Any `invalidateQueries` call on the areas key — even from unrelated Realtime events — immediately triggered a background refetch via the active Sidebar subscriber
- This caused the "3 POST /today" phenomenon observed in dev logs during JARVIS turns

With the fix:
- `initialDataUpdatedAt: Date.now()` marks the SSR-provided data as fresh at mount time
- `staleTime: Infinity` means the data never goes stale from TanStack's perspective; only Realtime `invalidateQueries` from actual Postgres `areas` table changes triggers a refetch
- The `useTableSubscription("areas", userId)` subscription remains fully active — legitimate area changes (insert/update/delete) still propagate

**SidebarTree audit result:** SidebarTree has NO `useQuery` with `initialData` for projects. Projects data flows through the `areas` prop (as `SidebarArea[].projects`), not a separate query. No patch needed.

**New test: `apps/web/tests/sidebar-no-refetch.test.tsx` (2 tests):**
- Test 1: `getAreasForCurrentUser` not called on mount when `initialData` is provided
- Test 2: `getAreasForCurrentUser` not called on remount (staleTime: Infinity keeps cached data fresh across React remounts — the core regression guard for the 3x POST issue)

### Task 2: validate-references batching + perf budget test

**New export in `apps/web/lib/jarvis/validate-references.ts`:**

Added `validateTurnReferences(userId, allProjectIds, calendarId)` which:
- Deduplicates `allProjectIds` via `Array.from(new Set(...))` before the SELECT (Pitfall 5 guard: multi-action turns referencing the same project don't fire duplicate identical SELECTs)
- Dispatches `validateProjectIds` + `validateCalendarId` concurrently via `Promise.all` — one "round-trip" for both
- Returns `{ projects: ValidateProjectsResult, calendar: ValidateCalendarResult }` typed as `ValidatedTurnRefs`

**Route wiring in `apps/web/app/api/jarvis/route.ts`:**

Added a conditional pre-validation step (step 7, before stream construction) that:
- Only fires when `body.linkedProjectIds.length > 0` — zero-project captures skip it entirely (no extra DB query)
- Builds `preValidatedProjectIds: Set<string>` and passes it into `ctx`

**Executor short-circuit in `apps/web/lib/jarvis/executor.ts`:**

New `resolveProjectIds(ctx, projectIds)` helper replaces the direct `validateProjectIds` calls in `createTask` and `createCapture`:
- If all model-emitted `project_ids` are in `ctx.preValidatedProjectIds`, returns a synthetic result immediately (no DB query)
- Falls back to full `validateProjectIds` validation when the model emits IDs not in the pre-validated set (defense-in-depth for prompt injection)

**`ExecutionContext` extended in `packages/jarvis-core/src/executor/interface.ts`:**

Added `preValidatedProjectIds?: Set<string>` as optional — backward-compatible. All existing tests that don't wire the route continue to work without this field.

**Drizzle logger hook in `apps/web/lib/db/client.ts`:**

Added `dbLogger` export — no-op in production (`undefined`, Drizzle skips logger call entirely), stub `{ logQuery: () => {} }` in test environment. Tests that count DB queries use `vi.mock("@/lib/db", ...)` directly (same pattern as existing jarvis tests) and count `db.select()` / `db.transaction()` calls.

**New test: `apps/web/tests/jarvis-perf-budget.test.ts` (4 tests):**
- `validateTurnReferences` fires exactly 2 SELECT queries (project + calendar) concurrently
- Returns correct `ValidatedTurnRefs` shape
- Deduplicates project IDs before querying
- Single-action JARVIS turn (mocked executor) fires ≤ 2 DB roundtrips via the route

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] TanStack `invalidateQueries` does not respect `staleTime: Infinity`**
- **Found during:** Task 1 RED test (second test assertion)
- **Issue:** The plan's test comment stated "staleTime: Infinity makes invalidate a no-op for refetch decisions on subscribed queries" — this is incorrect per TanStack Query 5.x source. `invalidateQueries` calls `refetchQueries` which bypasses staleTime entirely and refetches all active subscribers regardless of freshness.
- **Fix:** Redesigned the second regression test to guard against the ACTUAL root cause: React remount refetches (the "3 POST /today" mechanism). With `staleTime: Infinity`, cached data is never considered stale → remounts never trigger a fetch. The test now simulates unmount + remount (which is what the dev logs showed, not just invalidation).
- **Impact:** Test tests the correct behavior. The production fix (`initialDataUpdatedAt + staleTime: Infinity`) is correct and achieves the D-P2 #1 goal.
- **Commit:** `3da0289`

**2. [Rule 2 - Missing] `validateTurnReferences` skips calendar validation when called with null**
- **Found during:** Task 2 route wiring — the `validateCalendarId` with null fires a DB SELECT to get the default calendar even when no calendar action is in the turn
- **Fix:** Only call `validateTurnReferences` when `linkedProjectIds.length > 0`; skip calendar pre-validation at the route boundary (calendar is per-action, executor still validates per tool_use). This keeps the ≤ 2 DB roundtrip budget achievable for zero-project capture turns.
- **Commit:** `1f37009`

**3. [Rule 3 - Blocking] Test isolation issue in `jarvis-perf-budget.test.ts`**
- **Found during:** Task 2 test execution — the `validateTurnReferences` describe block shared the outer `beforeEach` which pre-populated `dbState.selectReturns` with route-specific rows, causing `validateTurnReferences` direct tests to consume wrong mock values
- **Fix:** Added an inner `beforeEach` in the `validateTurnReferences` describe that resets `dbState.selectReturns = []` before each direct-call test
- **Commit:** `1f37009`
