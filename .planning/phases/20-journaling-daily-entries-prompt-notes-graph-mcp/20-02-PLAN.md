Do NOT call `revalidatePath` anywhere — Realtime is the invalidation mechanism (Critical Pattern 3); captures.ts deliberately omits it and so must this file.

Define a shared date Zod schema: a string matching `^\d{4}-\d{2}-\d{2}$` refined to a real calendar date (reject "2026-13-40"). The day view passes a client-local "YYYY-MM-DD" string (CONTEXT specific: client-local day, never server UTC) — the action trusts that string as the canonical day key.

**1. `upsertJournalEntry`** — input Zod schema `{ date: <date schema>, mainResponse?: string (nullable, cap length e.g. 20_000 chars), notesSection?: string (nullable, same cap) }`. Behavior:
   - Validate input; on failure return the error ActionResult (same error shape captures.ts returns).
   - Resolve `userId` via getUserId(); if unauthenticated return the unauthorized ActionResult.
   - `await db.insert(journalEntries).values({ userId, date: input.date, mainResponse: input.mainResponse ?? null, notesSection: input.notesSection ?? null }).onConflictDoUpdate({ target: [journalEntries.userId, journalEntries.date], set: { ...only the provided fields..., updatedAt: sql\`now()\` } }).returning()`.
     - CRITICAL upsert semantics: build the `set` object from only the keys present in the validated input so an autosave that touches just `mainResponse` does not null out a previously-saved `notesSection` (and vice-versa). Always include `updatedAt` in `set`. The conflict target is the `(userId, date)` UNIQUE from plan 20-01 — this is what guarantees one row per day.
   - Wrap the write in `db.transaction` if captures.ts does for its mutations; otherwise a single statement is fine.
   - Return ok ActionResult with the upserted row.

**2. `getJournalEntry`** — input: a single date string (same date schema). Resolve userId; `db.select().from(journalEntries).where(and(eq(journalEntries.userId, userId), eq(journalEntries.date, date))).limit(1)`. Return ok with the row or `null`. The double predicate (userId + date) is the ownership guard in addition to RLS (defense in depth, mirroring captures' explicit userId filters).

**3. `getJournalEntries`** — input Zod schema `{ startDate?: <date>, endDate?: <date>, limit?: number (default e.g. 90, max e.g. 365) }`. Resolve userId; build a `where` with `eq(journalEntries.userId, userId)` plus optional `gte(date, startDate)` / `lte(date, endDate)`; `orderBy(desc(journalEntries.date))`; `.limit(limit)`. Return ok with the rows array (most-recent-first for the history feed in plan 20-04).

Import the Drizzle operators (`and`, `eq`, `gte`, `lte`, `desc`, `sql`) from the same module captures.ts imports them from. Implements JOURNAL-SERVICE-01.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → server action | The browser invokes journal actions with attacker-controllable args (date, text). Zod validation + getClaims-derived userId are the enforcement boundary; the action never trusts a client-supplied user id. |
| server action → Postgres | Drizzle statements run under the caller's identity; RLS (plan 20-01) plus explicit `userId` predicates double-gate every row. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-20-04 | Spoofing | client claiming another user's id in an action arg | mitigate | userId is derived from getClaims() server-side, never accepted as input; every query filters `eq(userId, <claims uid>)` and RLS re-checks. |
| T-20-05 | Tampering | autosave forking a day into duplicate rows | mitigate | onConflictDoUpdate on the UNIQUE(user_id, date) target collapses repeated writes to one row; Task 2 asserts toHaveLength(1). |
| T-20-06 | Denial of Service | oversized journal text payloads | mitigate | Zod caps mainResponse/notesSection length; invalid input returns a typed error ActionResult instead of executing the write. |
</threat_model>
