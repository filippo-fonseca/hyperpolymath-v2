<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser editor -> POST /api/jarvis/in-document | Client sends prompt + serialized page content + scope; server re-derives userId from getClaims and treats page content as untrusted reference-only data |
| runJarvisTurnStream -> executor -> Postgres/gcal | All writes go through createServerExecutor with server-validated IDs scoped to userId; serialized content grants reference-resolution context only, never write authority |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-31-01 | Spoofing | userId from client/model | mitigate | getClaims() at the route boundary; client/model userId ignored (Task 3) |
| T-31-02 | Tampering | Prompt injection via page content ("ignore previous instructions") | mitigate | Page content wrapped in a clearly delimited block + labeled untrusted/reference-only; executor still gates every action behind Zod + ownership, so injection can at worst yield a benign owned action, never a cross-tenant write |
| T-31-03 | Information Disclosure | Cross-tenant reference via injected context | mitigate | All write IDs (project_ids, calendar_id, entity ids) re-validated server-side in the executor against userId; reads scoped to userId |
| T-31-04 | Denial of Service | Oversized page content -> token/DoS | mitigate | MAX_CONTEXT_CHARS cap in the serializer (Task 2) + defensive length cap on pageContext in the route body validation (Task 3) |
| T-31-SC | Tampering | npm/pip installs | accept | Zero new packages this phase (RESEARCH Standard Stack: all deps already present) |
</threat_model>
