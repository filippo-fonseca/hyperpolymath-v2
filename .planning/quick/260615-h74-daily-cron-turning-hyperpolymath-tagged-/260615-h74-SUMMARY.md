# Quick 260615-h74: Daily cron turning hyperpolymath-tagged captures into GitHub issues Summary

A daily Vercel cron that reads the owner-user's "hyperpolymath"-tagged captures, gates and specs the genuinely actionable, public-safe ones through one claude-sonnet-4-6 call, and files them as GitHub issues on a public repo. Idempotent (once-per-day DB lock), bounded (25 per run), and auditable via four ordered, banner-commented security layers.

## What shipped

- **Schema (Task 1):** two additive NULLABLE columns on `captures` (`github_issue_url`, `github_evaluated_at`) and a new `cron_runs` table whose `UNIQUE (job_name, run_date)` index is the once-per-day lock. Migration FILE `0014_captures_to_issues.sql` generated additively; never applied.
- **Issue spec'er (Task 2):** `specCaptureAsIssue(content)` makes one forced-tool `claude-sonnet-4-6` call, Zod-validates the result, and fails closed to `{ actionable: false, ... }` on any error. The prompt encodes both an actionability gate and a public-safe privacy gate, and always tags `kiwi-drafted`.
- **Cron route (Task 3):** `GET /api/cron/captures-to-issues` with four ordered, individually banner-commented layers: (1) constant-time Bearer `CRON_SECRET` auth that fails closed and returns 401 before any DB/env/Anthropic work, 405 on non-GET; (2) once-per-day lock via `onConflictDoNothing` on the unique index, returning `{status:"already-ran"}` on conflict; (3) `PER_RUN_CAP=25` oldest-first limit; (4) env-resolved owner-only eligibility (`GITHUB_ISSUE_USER_EMAIL`, never hardcoded; unset/no-match is a no-op), `noExport` hard skip, `githubEvaluatedAt IS NULL`, hyperpolymath hashtag join. Issues are created via native `fetch` (no new deps); each capture is `try/catch`-isolated; `githubEvaluatedAt` is always set, `githubIssueUrl` only when issued; `cron_runs` is finalized; returns `{processed, issued, skipped, errors}`.
- **Wiring (Task 4):** `vercel.json` gains the `captures-to-issues` cron at `"0 6 * * *"` alongside the existing `snapshot-context` entry; `CLAUDE.md` gains a session-start section instructing Claude Code to run `gh issue list`, rank by tractability/leverage, present the ranking, and ask before starting.

## Migration safety (CRITICAL, honored)

- The migration was **generated as a FILE only** and **NEVER applied**. No `db:migrate`, `drizzle-kit migrate`, or `drizzle-kit push` was run. No live DB (local Docker, remote, or prod) was touched.
- `drizzle-kit generate` was deliberately NOT used. The Drizzle meta snapshots are frozen at `0009`, but `schema.ts` already contains ~10 later tables (habits, training, nutrition, integration_tokens, desktop_devices, etc.) that were added via hand-written SQL migrations `0010`-`0013` and are absent from `meta/_journal.json`. Running `drizzle-kit generate` would diff against the stale `0009` snapshot and emit a wrong, dangerous migration attempting to recreate already-applied tables. Per the plan's safety clause ("only then hand-write the .sql following the existing migrations' format"), `0014_captures_to_issues.sql` was hand-written to match the established `0010`-`0013` convention (`ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, `CREATE TABLE IF NOT EXISTS`, `CREATE UNIQUE INDEX IF NOT EXISTS`). The meta journal was intentionally left unchanged (9 entries, ending at `0009`), consistent with `0010`-`0013`.
- **User action required:** apply `apps/web/drizzle/0014_captures_to_issues.sql` to your local and/or remote DB yourself (the columns are additive/nullable and the table uses IF NOT EXISTS, so it is safe to apply to existing data).
