# Plan — Improve syntax highlighting + text-field outlines (issue #43)

## Problem

Two adjacent polish issues on the Jarvis surface, both rooted in token mismatches between intended design tokens and what shipped:

1. **Hashtag chips read as fluorescent lime, not sage.** `.hashtag-chip-inline` and `.hashtag-chip-live` in `globals.css` use raw Tailwind `rgb(101 163 13 / X)` (lime-600) as background, but pair it with `--ink-sage` text — a much more muted oklch token. The comment claims "Sage alpha register" but the value is pure lime. Same drift in `HashtagChip.tsx` (idle/hover/selected/new). The result is the "yellow-green tones" the issue flags as not on-brand.

2. **Input/Textarea focus state fights its own ring.** `globals.css` paints a calm neutral `--edge-hud` focus ring on every `input:focus-visible` / `textarea:focus-visible`. `Input.tsx` and `Textarea.tsx` then override `border-color` to `--ink-amber` on focus, so a focused capture field shows an amber border inside a cyan-ish ring. Inconsistent and visually noisy.

## Fix

Two atomic commits, both scoped to design tokens.

### Task 1 — Harmonize hashtag chip background with the brand `--ink-sage` token

Files:
- `apps/web/app/globals.css` (`.hashtag-chip-inline`, `.hashtag-chip-live`)
- `apps/web/components/captures/HashtagChip.tsx` (idle / hover / selected / new variants)

Action:
- Replace every `rgb(101 163 13 / X)` (Tailwind lime-600) with `color-mix(in oklch, var(--ink-sage) Y%, transparent)` so the chip background is derived from the actual sage ink token, not from a fluorescent lime placeholder.
- Switch inline editor chip text from `var(--ink-sage)` to `var(--ink)` (matches `HashtagChip` idle behavior) so the token has high readable contrast on the muted sage tint instead of sage-on-sage washout.
- Update inline docstrings/comments to reflect the new alpha register.

Verify:
- Visit the captures composer and Jarvis input. Type `#test`. Chip background should read as a muted parchment-friendly green, not fluorescent lime. Text should be dark ink and clearly legible.
- Selected state on `HashtagChip` (filter sidebar) should still be visibly distinct from idle/hover.

### Task 2 — Align Input/Textarea focus border with the calm global ring

Files:
- `apps/web/components/ui/input.tsx`
- `apps/web/components/ui/textarea.tsx`

Action:
- Remove `focus-visible:border-[var(--ink-amber)]` from both primitives. The global `input:focus-visible` / `textarea:focus-visible` rule in `globals.css` already paints both `border-color` and the ring as `--edge-hud` (the calm neutral). The amber override was leftover from an earlier "amber doc ring" iteration that the global rule already supersedes (see the inline comment at `globals.css:822` — text fields intentionally do NOT use the amber doc ring).
- Update docstrings on both primitives.

Verify:
- Click any non-Jarvis input (capture title, project name, etc.). Border + ring should both be the calm `--edge-hud` neutral, no amber.
- Jarvis input (agent-mode scope) should keep its cyan border + ring via the `.agent-mode-scope input:focus-visible` rule and inline-style overrides — untouched.
- Invalid state (`aria-invalid`) still goes coral.

## Scope guards

- Do NOT touch the project-chip (`.project-chip-inline`) color — it's the warm amber `$project` counterpart and is not in the complaint.
- Do NOT touch Jarvis input's cyan border/ring — agent-mode signature, intentionally distinct from journal inputs.
- Do NOT introduce a new design token; reuse `--ink-sage` and `--edge-hud`.
- Do NOT touch any other input across the app — global rule already covers them.

## must_haves

- All occurrences of `rgb(101 163 13 / ...)` (the lime placeholder) are removed from `apps/web/app/globals.css` and `apps/web/components/captures/HashtagChip.tsx`.
- Hashtag chip background derives from `var(--ink-sage)` via `color-mix`.
- Input + Textarea no longer override focus-visible border to amber.
- "Closes #43" appears in one of the atomic commit messages.
