<decisions>
These calls are made now so the executor does not re-litigate them mid-build.

DEC-1 — Anthropic API: live server-side fetch with a short cache, NOT a cron upsert.
The Cost API is a server-to-server call; `apps/web/.env.local` already holds `ANTHROPIC_ADMIN_KEY`, and the page is already `dynamic = "force-dynamic"`. So `getAnthropicApiUsage()` fetches the Cost API live on page load and caches in-process for 60s, exactly mirroring `getClaudeCodeUsage`'s cache shape. The `anthropic_api_usage` table is still created (per the task brief and for future cron/backfill), and `getAnthropicApiUsage` writes-through (best-effort upsert) the days it fetched so the table stays warm and a future cron can take over without a UI rewrite. If the live fetch fails, fall back to reading the table; if both fail, return `err(...)` so the panel shows an inline error and never crashes the page (D-06 Result contract). Rationale: simplest reliable option, no new cron infra, and the write-through means we are not throwing the data away. The known materialization caveat (cost_report can lag a few hours for the current UTC day) is acceptable because the chart is daily and the most recent bar self-heals on the next load.

DEC-2 — Claude Code subscription snapshots: a NEW small table `claude_subscription_usage`, NOT an extension of `claude_code_usage`.
`claude_code_usage` is keyed `(user_id, date)` and models per-day token totals. Session blocks (rolling 5-hour windows, identified by block start time) and weekly rollups (keyed by ISO week start) are different grains and should not be jammed into a per-day table. The new table holds at most a handful of rows per user (one "current session" snapshot keyed by block start, plus recent weekly rows keyed by week start) and is upserted by the same sync pipeline. Keep it deliberately small: store the latest active session block and the recent weekly rows; the laptop sync overwrites on each run.

DEC-3 — Percentages are computed against configurable Max-5x constants, never scraped.
True "% of Max-5x plan limits" is not available offline (already investigated — the rate-limit headers Claude Code's `/usage` reads are not persisted in JSONL, and there is no local usage/limit cache). So a small config module `limits.ts` exports session + weekly limit numbers (token-based and cost-based fields, whichever ccusage reliably gives) that the user can calibrate by hand. Every percentage rendered in the subscription panel is explicitly labeled approximate / based on configurable limits in the UI copy. Do NOT attempt to scrape or infer real plan limits.

DEC-4 — Migration numbering + application.
This worktree's latest drizzle SQL is `0015_kiwi_dev_runs.sql`. New migrations are `0016_anthropic_api_usage.sql` and `0017_claude_subscription_usage.sql`, written by hand to match the existing hand-authored style of `0012_claude_code_usage.sql` (plain `CREATE TABLE IF NOT EXISTS` with explicit PK + FK to `users`). The drizzle `meta/_journal.json` is already partial (it does not track 0012 or 0015), so do NOT attempt to regenerate or repair the journal; just add the SQL files alongside the others, matching the established convention in this repo.
</decisions>
